# Installing a Windows Site Mode agent from a join file

A join file (`*.fallow-join`) enrolls one machine into a LAN Site. It is a small
JSON document that names the coordinator, pins its certificate, and carries a
single-use enrollment token. It is sensitive and single-use: treat it like a
password on a USB stick, not a config file to keep around.

This path installs the prebuilt Go agent. The Python agent does not implement
Site Mode, so a join install always needs `-GoBinary`.

## What you need

- `agentctl.exe` for Windows (a GitHub Release asset, or `go build ./cmd/agentctl`).
- The llama.cpp build staged under `deploy\bin\windows\` (run
  `deploy\windows\fetch-llama.ps1` first).
- The `.fallow-join` file for this site, generated by the coordinator operator
  with `flw site join-bundles --count N --output DIR`.

## Install

```powershell
deploy\bootstrap.ps1 -JoinBundle C:\path\to\site.fallow-join -GoBinary C:\path\to\agentctl.exe
```

`bootstrap.ps1` reads the machine, then hands off to `install.ps1`, which:

1. Validates the join file before it touches anything. A malformed file, an
   unknown field, a non-HTTPS coordinator URL or a bad pin stops the install
   with nothing written.
2. Copies the join file into `%USERPROFILE%\.fallow\site\join.json` and locks
   it down so only your account can read it.
3. Renders `%USERPROFILE%\.fallow\agent.toml` token-free: it references the
   join file and binds llama to `127.0.0.1`. The token is never written into the
   config or the task arguments.
4. Registers the at-logon Scheduled Task `Fallow\FallowAgent`, running
   `agentctl run -config`.

On first run the agent enrolls itself from the join file, persists a token-free
identity, and removes its copy of the token. After that the machine resumes Site
Mode from the stored profile across reboots without the join file.

`install.ps1` is idempotent. Re-running keeps a live config and your edits (for
example the `llama_server_binary` path) and never replaces an existing identity.

## After enrolling: remove the original

The installed copy of the token is removed once enrollment succeeds, but the
**original** `.fallow-join` on the USB stick or MDM share still contains a live
token until it is used. Remove it once the machine is enrolled. A single-use
token that has been consumed is inert, but do not leave copies lying around.

## Check the install

```powershell
deploy\windows\doctor.ps1
```

`doctor.ps1` prints one JSON object covering the Scheduled Task, the logged-in
session, config and join-file permissions, the loopback bind, the llama binary,
the pinned-TLS check and the stored identity. It exits non-zero if a required
check fails. Add `-Probe` to also test live reachability to the coordinator,
which tells a blocked port, a TLS-intercepting proxy and a pin mismatch apart.

## Loopback only, never the LAN

Site Mode serves llama replicas over `127.0.0.1` only. llama-server has no
authentication, so a LAN bind would be an open endpoint. The config refuses a
non-loopback `bind_host` in Site Mode, and `doctor.ps1` fails if any replica
port is listening off loopback. Nothing here opens a firewall port; coordinator
traffic is outbound HTTPS to the pinned URL.

## Firewall, proxy and TLS

- **Firewall:** the agent makes outbound HTTPS connections to the coordinator.
  It needs no inbound rule. Do not add one for llama.
- **Proxy:** Site clients ignore WinHTTP, PAC and WPAD proxy settings and do not
  follow redirects. An intercepting proxy breaks the certificate pin by design;
  `doctor.ps1 -Probe` reports it as a pin mismatch. The fix is to exempt the
  coordinator host from interception, not to relax the pin.
- **TLS:** trust comes from the pinned SubjectPublicKeyInfo hash in the join
  file, not the Windows trust store. A wrong pin is a hard failure with no
  network reset; recovery is a new join file distributed locally.

## Honest gaps

These are not proven by sandbox tests and remain manual gates before a school
pilot: Defender/SmartScreen or EDR allowlisting, VLAN and institutional-firewall
egress to the coordinator, power-policy sleep behaviour, and identity survival
across profile cleanup or a reimaging product such as Deep Freeze.
